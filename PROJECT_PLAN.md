# FrameFlow — план программы обработки и публикации видео

Дата: 23 октября 2026 года.

Этот файл — актуальная спецификация по результатам обсуждения. Исходный `survivalflow_studio.md` сохранён как первоначальная концепция; обещания гарантированного антибана, скорости обработки и сроков разработки из него не являются требованиями или подтверждёнными фактами.

## 1. Главная идея

Пользователь создаёт готовые видео вместе с ИИ в отдельном проекте «Банерка». Здесь строится локальная программа, которая принимает эти видео, накладывает рекламный баннер, создаёт отдельный вариант для каждого выбранного аккаунта, публикует по расписанию и собирает результаты в одной панели.

Главная ценность: сократить ручной монтаж, переключение между аккаунтами и сбор статистики. Генерация сценария, озвучки и самого исходного видео остаётся в «Банерке».

## 2. Что уже согласовано с пользователем

- Программа запускается на компьютере пользователя под Windows.
- Фоновая работа возможна, пока компьютер включён, не спит и процесс программы запущен.
- На старте: 3 аккаунта TikTok и 3 канала YouTube.
- Объём: 3 исходных ролика в сутки, каждый на все 6 аккаунтов — всего 18 публикаций.
- Для каждого исходника создаётся 6 отдельных вариантов, по одному для каждого аккаунта.
- Баннер загружается отдельно. Время появления задаётся вручную либо определяется как середина видео.
- Варианты отличаются умеренными фильтрами: цвет, контраст, насыщенность и при необходимости небольшое кадрирование.
- Первая версия включает весь основной конвейер: баннер → варианты → публикация → статистика.
- Возможность подключить ИИ к статистике закладываем в архитектуру. Gemini предлагается как последующее расширение; включение ИИ-разбора в первую версию отдельно не согласовано.

## 3. Утверждённый технологический стек

Основной стек согласован с пользователем 23 октября 2026 года: Python + FFmpeg + FastAPI + React/TypeScript + SQLite + APScheduler. Способ TikTok-интеграции остаётся предметом технической проверки. Gemini — последующее расширение.

| Часть | Решение | Зачем |
| --- | --- | --- |
| Основная логика | Python 3.12+ | Обработка задач, работа с API, расписание и аналитика |
| Обработка видео | FFmpeg и ffprobe, запуск из Python | Баннеры, фильтры, проверка форматов и экспорт |
| Локальный API | FastAPI + Pydantic | Связь панели, базы и обработчиков; проверка входных настроек |
| Интерфейс | React + TypeScript + Vite | Удобный предпросмотр, настройки баннера, очередь, календарь и графики |
| Хранение данных | SQLite + SQLAlchemy; миграции схемы | Аккаунты, ролики, варианты, задачи, публикации и история метрик |
| Расписание | APScheduler + отдельный рабочий процесс | Запуск готовых задач и сбор статистики независимо от вкладки браузера |
| YouTube | Google API Python Client + OAuth | Публикации через Data API, отчёты через Analytics API |
| TikTok | Отдельный адаптер, способ подключения проверяется первым | Возможность заменить метод публикации без переделки остального приложения |
| ИИ-разбор | Google Gen AI SDK / Gemini, следующий этап | Анализ подготовленных таблиц статистики |
| Секреты | Windows Credential Manager / DPAPI | Защита токенов; данные браузерных сессий не помещаем в исходники и логи |

### Почему Python, а не Rust

В этом проекте основная нагрузка — кодирование видео и сеть. Видео кодирует FFmpeg; Python управляет процессами и API. Переписывание такой управляющей логики на Rust само по себе не ускорит рендер.

Python выбран основным языком первой версии. Rust можно рассмотреть позже для нативной оболочки или конкретного узкого места, подтверждённого измерениями. На старте отдельная кодовая база на Rust добавит работу без очевидной пользы для нагрузки в 18 публикаций в день.

React и TypeScript нужны для интерфейса. По запросу пользователя от 25 октября 2026 года основной запуск открывает отдельное окно Windows через pywebview/WebView2, без вкладок и адресной строки. API по умолчанию слушает только `127.0.0.1`; тот же локальный интерфейс остаётся доступен из браузера для диагностики. Публичный сайт или облачный сервер не нужны. API и worker работают независимо от окна; его закрытие не останавливает очередь. Повторный запуск возвращает существующее окно. Несохранённые правки требуют подтверждения закрытия.

Для постоянного интерфейса с предпросмотром, настройками баннера и очередью выбран React. Streamlit не входит в утверждённый стек. Docker, Redis и PostgreSQL на старте не требуются.

## 4. Пользовательский сценарий

1. Пользователь добавляет один или несколько исходных видео из проекта «Банерка».
2. Программа проверяет длительность, размеры, ориентацию, звук и возможность декодирования.
3. Пользователь загружает баннер и выбирает время появления: свой таймкод или середина.
4. Настраивает длительность показа, положение и размер. Баннер накладывается поверх. С 26 октября доступен переключатель «Стоп-кадр на время баннера»: изображение замирает, исходный звук прерывается тишиной, затем оба продолжаются; длительность увеличивается на время баннера. При выключенном переключателе видео идёт непрерывно, его длина не меняется.
5. Пользователь выбирает аккаунты, описание и время публикации для каждого назначения.
6. Программа показывает предпросмотр с баннером и настройками варианта.
7. «В очередь» → время → «Запустить автозалив»: программа сама рендерит и отправляет выбранные варианты, без второго подтверждения. Выключенный флажок автозалива оставляет режим подготовки MP4.
8. Для опубликованного ролика сохраняются платформа, аккаунт, ссылка, идентификатор и время публикации.
9. Статистика обновляется по расписанию и доступна для сравнения роликов и каналов.

## 5. Обработка видео и баннера

### Первая версия

- Основной вход: MP4; поддержка других контейнеров определяется доступными декодерами FFmpeg и проверяется при импорте.
- Баннер: PNG с прозрачностью и видео MOV/MP4 при поддерживаемом кодеке. Прозрачность видео зависит от кодека, а не только расширения файла. GIF можно добавить после проверки работы анимаций.
- Время появления: вручную или 50% длительности. Поиск тишины не требуется для первой версии.
- Отдельная настройка длительности показа. Без стоп-кадра баннер должен помещаться до конца видео. Со стоп-кадром точка вставки должна быть раньше конца исходника, а длительность баннера добавляется к результату. Старые задания не изменяются.
- Размер и позиция баннера задаются относительно кадра; нужен предварительный просмотр.
- Анимация баннера начинается в момент появления, а не с начала исходного ролика. Поведение короткого баннера — повтор или удержание последнего кадра — задаётся явно.
- Предлагаемый формат экспорта для вертикальных роликов: 1080×1920, H.264, yuv420p, AAC при наличии звука. Режим кадрирования или полей выбирается явно.
- Исходник без аудио обрабатывается без ошибки. С 26 октября 2026 звук видеобаннера включается настройкой «Звук баннера». Во время рекламы он заменяет звук исходника, после возвращается исходная дорожка; со стоп-кадром мультфильм продолжается с точки паузы. Если аудио рекламы короче показа: удержание кадра даёт тишину после конца аудио, режим повтора повторяет и звук. При выборе/импорте баннера автоматически включается стоп-кадр, звук включается при наличии аудиодорожки. Старые задания не меняются.
- С 3 ноября 2026 (удержание зрителей): «Рекламу — в паузу речи рядом с серединой» — при импорте видео находятся паузы речи (громкость каждые 50 мс относительно громких участков дорожки, поэтому фоновая музыка не мешает); реклама начинается в паузе, ближайшей к середине, не дальше min(3 с, 5 % длины). Нет паузы — ровно середина. Сдвиг показывается в проверке БУБА предупреждением (допуск «середины» модерацией не опубликован), сдвиг больше окна остаётся ошибкой. «Медленный наезд камеры на стоп-кадре» — удерживаемый кадр плавно приближается на 6 %, звук ролика по-прежнему ставится на паузу. Предупреждение, если звук рекламы без стоп-кадра заглушает речь. Для новых видео обе настройки включены по умолчанию; старые исходники и задания не меняются, паузы для ранее импортированных видео вычисляются при сохранении настроек.
- Аппаратный кодировщик используется только после проверки доступности и результата. Должен быть запасной программный вариант.
- Прогресс рендера, отмена, понятные ошибки и очистка временных файлов.

### Варианты для аккаунтов

Для каждой пары «исходник + аккаунт» сохраняется свой набор параметров: яркость, контраст, насыщенность, при необходимости кадрирование. Настройки сохраняются, чтобы повторный запуск давал воспроизводимый результат.

Фильтры должны сохранять читаемость текста, баннера и качество изображения. Изменение скорости и звука не входит в базовую обработку. Поддельные GPS, модель телефона и другие вымышленные метаданные не требуются.

Технически разные файлы не гарантируют признание контента оригинальным, отсутствие ограничений, монетизацию или попадание в рекомендации.

## 6. Публикация и подключение аккаунтов

### YouTube

Основной путь — официальный YouTube Data API, подключение каждого канала через OAuth. Сохраняем и показываем фактический идентификатор канала, чтобы не перепутать назначения.

Нужно проверить разрешения и ограничения конкретного проекта Google Cloud. Актуальная документация `videos.insert` прямо указывает, что непроверенные API-проекты не ограничены закрытой видимостью только по факту отсутствия проверки. Тем не менее рабочую публикацию с нужной видимостью подтверждаем тестом на конкретном канале.

Расписание может исполняться платформой, когда ролик заранее загружен и запланирован через API. Если задача ещё локальная, выключенный компьютер её не отправит. Статусы «загружено», «обрабатывается», «запланировано» и «опубликовано» различаются.

### TikTok

Это главный вопрос технической проверки перед основной реализацией.

- Direct Post API требует разрешений и аудита для снятия ограничения закрытой видимости.
- В Intended Use TikTok прямо исключает приватную утилиту для аккаунтов владельца/команды из допустимого сценария Direct Post. Нельзя закладывать получение такого допуска как гарантированный путь.
- В guidelines также есть ограничения на добавляемые приложением рекламные надписи и брендинг. Совместимость сценария рекламного баннера с выбранной интеграцией требуется проверить отдельно.
- `wkaisertexas/tiktok-uploader` рассматривается как кандидат браузерного адаптера. README не доказывает работоспособность с аккаунтами пользователя; нужен отдельный тест.
- Реализуется интерактивный вход: отдельный непостоянный контекст Chrome открывает официальный сайт TikTok; пользователь сам проходит вход и проверки. Программа ищет ссылку собственного профиля в навигации либо собственную страницу с действием редактирования, требует действующую cookie сессии и отдельное подтверждение найденного @имени в панели. Пароль приложение не читает и не сохраняет. Если профиль не определён однозначно, подключение не отмечается успешным. Это браузерная проверка с подтверждением пользователя, не официальный OAuth и не получение неизменяемого ID через API.
- Сессия и состояние TikTok сохраняются через Windows DPAPI. Доступны отмена и таймаут 10 минут; отменённый вход не может позднее сохранить сессию. Есть защита повторного подключения того же @имени и смены аккаунта у записи с заданиями.
- Google может отклонить вход из управляемого браузера. Для TikTok предусматриваются QR-код из официального приложения на телефоне и уже привязанные телефон/почта. Отказ Google показывается как требующее действия состояние; по кнопке пользователя выполняется обычный возврат на TikTok/login. Маскировка автоматизации и отключение защит не входят в реализацию. Реальный результат альтернативного способа проверяется отдельно.
- Состояние `browser_login` подтверждает сохранённый вход, но не разрешает непроверенную автоматическую загрузку. Разрешение отправки остаётся отдельной проверкой адаптера/ID/видимости. Статистика TikTok требует отдельной интеграции.
- Авторизация и требуемые подтверждения выполняются пользователем. При истечении сессии, CAPTCHA или проверке аккаунта задача получает статус «требуется действие».
- Запасной путь при недоступной автоматической публикации: подготовленный файл и описание для ручной загрузки. Этот режим не считается выполнением требования автопубликации.

Способ публикации и способ получения статистики — отдельные интеграции. Рабочая загрузка в TikTok не означает автоматически наличие доступа к его аналитике.

## 7. Статистика

### YouTube

Через Data API и Analytics API, при выданных правах и поддерживаемых отчётах: просмотры, вовлечённые просмотры, лайки, комментарии, время просмотра, средняя длительность/процент просмотра и подписки от видео. Метрики могут поступать с задержкой; интерфейс показывает время последнего обновления.

### TikTok

Стандартный Video Object Display API содержит просмотры, лайки, комментарии и репосты. Доступ зависит от одобрения приложения и прав аккаунта. Полноценное удержание, время просмотра и источники трафика через этот интерфейс не обещаем. Для недоступных метрик возможен импорт выгрузки пользователя.


Для подключённых через Chrome аккаунтов без отдельного Display API токена доступны публичные счётчики конкретного опубликованного ролика: просмотры, лайки, комментарии и репосты. Читается страница TikTok без cookies с обязательным совпадением ID и автора, источник — TikTok public page. Это накопительные публичные данные с возможной задержкой, не внутренняя аналитика Studio. Отсутствующие/некорректные поля не заменяются нулями; ошибка чтения сохраняет предыдущие снимки. Почасовое обновление и ручная кнопка используют этот путь; изменения сайта могут сделать его недоступным.

### Что показывать в панели

- Таблица каналов с результатами за выбранный период.
- Таблица роликов со ссылками, аккаунтами, состоянием и последними метриками.
- Графики роста показателей, рассчитанные по сохранённым снимкам счётчиков.
- Сравнение вариантов одного исходника через одинаковое время после публикации: например, 24 часа и 7 дней.
- Раздельное отображение данных платформ: определения просмотров могут отличаться.
- Отсутствующие данные показываются как «нет данных», а не как нулевой результат.

Периодические снимки накопительных счётчиков дают приблизительную динамику с момента подключения; они не восстанавливают неизвестную историю. YouTube Analytics отдельно позволяет запросить доступные исторические отчёты.

## 8. ИИ-анализ — последующее расширение

Сбор статистики выполняют интеграции платформ. Gemini получает подготовленные агрегаты, параметры вариантов, тему ролика и время публикации. Ему не передаются токены доступа.

Примеры полезных запросов:

- Какие темы и каналы показывают лучшие результаты за первую неделю?
- Какие следующие сюжеты и варианты баннера стоит протестировать?
- Где результаты ниже обычных для этого канала?
- Достаточно ли данных для вывода или пока есть только предположение?

Выводы сопровождаются цифрами и периодом сравнения. Различия между каналами нельзя автоматически приписывать цветовому фильтру. ИИ не меняет расписание и не запускает публикации самостоятельно в базовом сценарии.

Postiz распространяется под AGPL-3.0. Его код не планируется переносить в приложение; если потребуется заимствование, сначала определяем применимые условия лицензии. Самостоятельное развёртывание Postiz не предоставляет автоматически одобрений TikTok/YouTube.

Общее правило: по возможности подключаем библиотеки, а не копируем целые проекты. При заимствовании кода сохраняем сведения об авторстве и лицензии, фиксируем источник и версию. Версии зависимостей и заимствованных фрагментов фиксируются после технической проверки.

Репозитории из первоначальной концепции для браузерной загрузки YouTube, антидетект-движок и ExifTool сейчас не выбраны. Для ручного таймкода и вставки по середине pydub не нужен.

## 10. Устройство программы и хранение данных

```text
Локальная панель React
        │
        ▼
FastAPI ─────────────── SQLite
        │                  ▲
        ▼                  │
Рабочий процесс: расписание и выполнение задач
        ├── FFmpeg: баннер и варианты
        ├── адаптер YouTube: загрузка и проверка состояния
        ├── адаптер TikTok: после технической проверки
        └── сбор статистики → снимки метрик
                                  │
                                  └── Gemini: опциональный анализ
```

Минимальные сущности базы:

- `accounts`: платформа, идентификатор канала, имя, состояние доступа; ссылки на защищённые секреты.
- `videos`: исходник, длительность, параметры, контрольная сумма и тема.
- `banners`: файл и сведения о формате/анимации.
- `variants`: исходник, аккаунт, настройки баннера/фильтров, путь экспорта.
- `jobs`: тип задачи, время запуска, состояние, попытки и ошибка.
- `publications`: вариант, аккаунт, внешний ID, ссылка и подтверждённое состояние публикации.
- `metric_snapshots`: публикация, время получения и доступные показатели.

Экспортированные видео хранятся файлами, а не внутри SQLite. Срок хранения настраивается; исходники не удаляются автоматически. Логи не содержат секреты и cookies.

## 11. Очередь, сбои и расписание

- Источник истины для задач — база, а не открытая вкладка и не только память планировщика.
- Рендер и загрузки не выполняются внутри обработчика интерфейса.
- Один рабочий процесс на старте; ограничиваем число одновременных рендеров и загрузок.
- Перезапуск программы не теряет список задач.
- Уникальный ключ публикации связывает вариант и аккаунт, чтобы обычный повтор задачи не создавал второй пост.
- Если загрузка могла завершиться, а ответ потерян, сначала проверяем результат. Если однозначная проверка невозможна, показываем «результат неизвестен» и требуем сверки перед повтором.
- Повторяем временные сетевые ошибки с задержкой; ошибки авторизации требуют действия пользователя.
- После сна/выключения пропущенные публикации помечаются. Предлагаемый режим: пользователь решает, перенести их или запустить сейчас; не публикуем все накопленные задачи разом.
- Время хранится в UTC, в интерфейсе используется выбранный часовой пояс; первоначально Europe/Moscow.
- Резервное копирование базы и настройки срока хранения файлов.

## 26 октября — первая автоматическая отправка TikTok

Реализован отдельный Playwright-адаптер backend/tiktok_upload.py, ориентированный на DOM-селекторы wkaisertexas/tiktok-uploader 1.2.0 (MIT). Нет stealth-настроек, чтения профиля Chrome или повторного клика публикации при ошибке. Обычный Chrome используется для входа через расширение; отправка открывает отдельное служебное окно Chrome с сохранённой DPAPI-сессией.

Для browser_login обычная массовая отправка остаётся закрыта. Пользователь может подтвердить первую публикацию конкретного готового задания (файл, аккаунт, видимость) действием test_upload. В jobs миграция 4 добавляет validation_upload=false; test_upload включает его только для выбранного задания и сбрасывает старое расписание — это отправка сейчас.

Адаптер проверяет собственный профиль, неизменность сессии, описание, явный выбор видимости, готовность формы; сохраняет контрольную точку перед публикацией. При доказанной ошибке до клика сбрасывает одобрение, позволяет исправить проблему; при возможном клике и потере ответа ставит unknown без повтора. Успешное подтверждение требует положительного ответа операции публикации и одного цифрового ID; bool и сообщение об успехе без ID недостаточны. ID и ссылка сохраняются, статус platform_processing не означает подтверждённую публичную видимость. browser_verified выставляется только после такого ответа, не после входа. ИИ-пометка включается при synthetic=true, при неизвестном контроле отправка останавливается.

Локальные тесты на настоящем Chromium с синтетическими страницами проверяют public/private, неверный профиль, отсутствие поля видимости, ответ без ID, потерю ответа, единственный POST, checkpoint, интеграцию worker и запрет повтора. Они не заменяют реальную проверку TikTok. После этого остаются: подтверждение настоящей публикации, проверка обработки/видимости и метрики.

## 26 октября — режим БУБА и комментарии

По запросу пользователя реализован режим соответствия правилам https://mediabuba.ru/pravila (прочитана версия от 16 сентября 2026). Это локальные измерения и ручные подтверждения, не гарантия модерации/выплаты и не распознавание прав на контент. Новые импорты включают buba_mode, описание получает #бубавпн без дублей. По умолчанию buba_required=true запрещает отправку старых вариантов без режима; в настройках можно явно вернуть общий режим. Настройки существующего черновика подготовлены, экспортированные файлы и задания не переписываются.

Проверки перед одиночным/пакетным одобрением и прямо перед отправкой: 10–300 секунд итогового видео с учётом стоп-кадра; анимационный баннер, середина, X/Y=50%, геометрическая площадь от 25%, непрозрачность, полный показ рекламы, её звук при наличии, #бубавпн и public. Для 2+ минут отправка пока заблокирована до уточнения неоднозначных таймингов нескольких баннеров. Голос/аудитория/права/отсутствие хромакея и запрещённого содержания/оформление шапки/отсутствие накрутки и Promote подтверждаются человеком. Измеряется рамка, а не число непрозрачных пикселей.

banner_height — опциональная высота в процентах. Кнопка подгонки задаёт 100% ширины, 26% высоты, центр и полную длину рекламы. Это явное изменение пропорций с сохранением всего изображения; предпросмотр и FFmpeg используют одинаковую геометрию. Возврат к исходным пропорциям доступен.

Миграция SQLite 5 добавляет buba_submissions, comments, comment_scans. Локальный учёт заявки требует подтверждённых пользователем даты и публичности, ID ролика, 10 000 просмотров из снимков и срока до 8-го календарного дня по Europe/Moscow (граница — 00:00 даты публикации +7 дней; это консервативный расчёт). Повторная отметка исходника с тем же SHA256 с другого аккаунта/платформы запрещена; отменить уже поданную заявку или повторить отказанную нельзя. Семантически одинаковые видео с разными SHA автоматически не распознаются. Заявка в бот и запись экрана с телефона остаются ручными.

Комментарии: read-only мониторинг, локальная очередь подозрительного рекламного спама, ссылки/приманки в профиль, отметка ручной проверки. Это эвристики, а не доказанный спам; удаление на платформах не выполняется. YouTube использует официальный API commentThreads.list и comments.list для ответов, с пагинацией и пределом 10 запросов за проход; ограничение объёма показывается как partial. Ошибка доступа — unavailable с сохранением ранее замеченных подозрений.

TikTok читает только видимые комментарии через отдельный headless Chrome с сохранённой сессией и проверкой собственного профиля. Всегда partial, при недоступной разметке/входе — unavailable. Коммерческое использование Research API не заявляется. Чтение реальных комментариев пользователя ещё не подтверждено. Настроить встроенные фильтры TikTok и вручную удалять настоящий спам по-прежнему необходимо.

Фоновая проверка запускается каждые 15 минут отдельным executor, максимум 2 ролика за проход из последних 30 с ID и режимом БУБА; это не обещание проверки каждого ролика раз в 15 минут. Для любого задания есть ручная кнопка обновления. Никакие профили/описания/комментарии на площадках автоматически не изменялись в ходе внедрения.

## 26 октября — подтверждён первый TikTok-ролик

Устранён реальный сбой описания: редактор TikTok терял букву при слишком быстром вводе (#ббавпн вместо #бубавпн). Ввод проверяет Unicode/служебное форматирование, при непринятой вставке использует последовательные события с паузой 80 мс. Важные символы, регистр и emoji-joiner не удаляются. После стабилизации и прямо перед публикацией повторно проверяются описание и видимость. При несовпадении кнопка не нажимается. В логах только размеры/категории символов, без полного описания и секретов.

После клика TikTok может перенаправить в Studio без поддержанного publish-response с ID. Тогда адаптер читает ответ /tiktok/creator/manage/item_list/v1/ при штатной навигации Studio и сопоставляет описание, длительность (+/-1 сек), время создания (окно попытки), собственный аккаунт и единственный ID. Два кандидата не считаются подтверждением. Повторной публикации при сверке нет. Для старого unknown добавлен POST /api/jobs/{id}/tiktok-result и кнопка «Проверить результат TikTok». ID не присваивается второму заданию того же аккаунта.

## Уточнение — YouTube: ошибка доступа до отправки и настоящий unknown, 02.11.2026, 21:29 МСК

В отправке YouTube отдельно отслеживается начало вызова request.next_chunk. Подготовка OAuth, проверка владельца, построение запроса и чтение MP4 до этого вызова не означают отправку. Если на этом этапе Google RefreshError/ошибка идентичности, задание становится waiting_auth, канал connected=false, разрешение снимается, upload_started_at очищается. Сетевая/локальная ошибка до отправки даёт ready с явной причиной. После начала сетевой отправки возможная потеря ответа по-прежнему даёт unknown без автоматического повтора. Диагностика не сохраняет OAuth payload/токены; известные причины квоты и доступа отображаются безопасным текстом.

У серии 04 старый общий обработчик сохранил unknown без точного этапа. При текущей безопасной проверке Google вернул invalid_grant (вход истёк или отозван). Канал помечен требующим входа, текст ошибки уточнён; unknown, external_id и отметка прежней попытки сохранены. Пока владелец не войдёт и канал не будет сверён, повторная загрузка не разрешается. Сохранённые credentials не удалялись; пароль/коды вводит сам пользователь в Google.

Проверка: первоначально 47 тестов прошли, один старый тест интервала использовал исключение при построении videos.insert как имитацию сетевой отправки. Его имитация перенесена на next_chunk, где действительно начинается сеть. Затем все 22 проверки публикации/библиотеки и исправленного теста интервала прошли; Ruff и diff check успешны. API/worker обновлены, настоящая публикация не выполнялась. Авторизация и сверка реального канала требуют участия владельца.


## Рост и защита автозалива — 06.11.2026

По запросу пользователя (выбор из разбора похожих проектов 05.11.2026) добавлены в ветке `growth-tools`:

- **Проверка входа перед автозаливом.** Кнопка «Запустить автозалив» сначала проверяет вход в каждый выбранный канал только чтением: YouTube — обновление токена и `channels.list(mine)`, TikTok — скрытый браузер с сохранённой сессией и проверка профиля. Доказанная проблема входа (`auth`) останавливает запуск. Worker каждые 5 минут перепроверяет каналы с публикацией в ближайшие 45 минут (YouTube не чаще 30 минут, TikTok — 6 часов, канал с проблемой — каждые 30 минут); при проблеме задания переходят в `waiting_auth` до начала загрузки, подключение аккаунта не сбрасывается. Ошибка сети или квоты (`error`) ничего не меняет. Успешная проверка или переподключение возвращают задания.
- **Лучшее время.** Просмотры за первые 24 часа (интерполяция по снимкам) делятся на медиану канала, группировка по часу публикации (МСК), соседние часы с весом 0,5. Совет: лучший проверенный час; каждый третий ролик — проба мало проверенного часа в окне 8–23; без данных — 18:00 YouTube, 19:00 TikTok. Каналы с медианой меньше 20 просмотров (TikTok с регионом FI) по часам не оцениваются. В очередь передаётся время для каждого канала (`schedules`), оно не входит в отпечаток варианта.
- **Комментарий автора.** `Job.extras.comment` (миграция 9: `jobs.extras`). Публикуется один раз после статуса `published`, кроме приватных роликов и «для детей». Перед отправкой ищется такой же комментарий канала, поэтому повтор не задваивает его; сбой — `failed` без автоповтора. YouTube: `commentThreads.insert` с правом `youtube.force-ssl`, которое запрашивается только при новом входе; старые токены обновляются со своими правами. Закрепления в YouTube Data API нет — ссылка `watch?v=…&lc=<id>` для закрепления в 2 клика. TikTok: публикация и закрепление через сохранённую сессию на странице ролика.
- **TikTok: звук и авторские права.** Звук из «Избранного» по словам названия, громкость добавленной дорожки ~10 %; если трек или регулятор не найден — редактор закрывается без сохранения, ролик выходит без звука. Проверка авторских прав TikTok (`tiktok_copyright`: off / warn / strict, по умолчанию warn): найденная проблема всегда останавливает публикацию до кнопки «Опубликовать»; незавершённая проверка останавливает только в strict. Селекторы — по tiktokautouploader (MIT).
- **Сервер: конкуренты и отчёт времени.** `/opt/frameflow/stats/competitors.py` (таймер каждые 3 часа): последние 30 роликов каналов-конкурентов, рост за 24 часа, кратность к медиане канала, часы публикаций хитов, кандидаты из поиска коротких видео по нише. `data/best_time.md` пересчитывается часовым сборщиком. Копия — `tools/server-stats/`.

Проверено на VPS: новые тесты (preflight, best time, extras, комментарии, звук и авторские права на локальных страницах Chromium), прежние тесты без новых падений, Ruff, сборка интерфейса, снимки 1024×600 на временной базе (`docs/validation/growth/`). Не проверено: Windows-ноутбук, реальные TikTok и YouTube (комментарии, закрепление, звук, проверка прав, вход), переподключение YouTube с новым правом.
