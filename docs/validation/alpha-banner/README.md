# Чёрный фон WebM-баннера — 02.11.2026

Причина подтверждена на настоящем `data/uploads/1e2acf9cc9134302b79e31b0c26047a2.webm`: VP9, alpha_mode=1. Декодирование штатным native VP9 теряет отдельную альфа-плоскость: PNG alpha=(255,255), угол RGBA=(0,0,0,255). Принудительный libvpx-vp9 сохраняет alpha=(0,255), угол=(0,0,0,0). Чёрная область уже присутствует в локальном экспортированном MP4 до отправки на платформу.

Исправление: backend/media.py выбирает libvpx/libvpx-vp9 перед входом WebM-баннера для миниатюры и рендера. Срабатывает и для старого импорта, где в метаданных нет has_alpha. probe теперь сообщает этот признак. Не используются удаление чёрного по цвету или изменение содержимого баннера.

Проверены настоящий баннер на локальном фрагменте и два регрессионных теста с реальным FFmpeg (VP8/VP9): прозрачная область показывает синий исходник, непрозрачная — красный баннер, после интервала баннер исчезает; миниатюра сохраняет альфа-канал. Ruff успешен. Общий pytest: 184 passed, 3 failed за 279,28 с. Все проверки обработки видео прошли; три ошибки — ожидания браузерных сценариев TikTok (Google denial/cancel, interactive login, upload no_id). Отдельный повтор этих трёх без изменений кода: 3 passed за 36,03 с. Это повтор нестабильных браузерных проверок, а не единый чистый прогон 187 тестов.

API и worker перезапущены из командной строки, heartbeat подтверждён. Активных рендеров/отправок при перезапуске не было. База, задания, старые MP4 и публикации не заменялись. Новые экспорты используют исправление. Существующие MP4 автоматически не исправляются: для них нужен новый рендер, а не простая повторная отправка прежнего файла.

Артефакты: native.png и libvpx.png — декодирование одного кадра; published-local.png — кадр прежнего локального MP4; corrected-frame.png и corrected-preview.mp4 — проверочный локальный фрагмент с настоящим баннером. Никаких публикаций или изменений на YouTube/TikTok не выполнялось.
