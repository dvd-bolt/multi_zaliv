# FrameFlow

Ранее — SurvivalFlow. Название изменено по выбору пользователя 29.10.2026. Рабочая папка multi_zaliv, SURVIVALFLOW_* и технический идентификатор health сохранены для совместимости с существующими данными и скриптами. Новые команды запуска: Start FrameFlow.cmd и Stop FrameFlow.cmd; прежние команды продолжают работать.

Закрытый репозиторий: [dvd-bolt/multi_zaliv](https://github.com/dvd-bolt/multi_zaliv).
Git хранит исходники, документацию и материалы проверок. Папка `data/` (база, видео, сессии и локальные настройки), секреты, зависимости и сборка остаются на компьютере и не входят в репозиторий.

Локальная монтажная для Windows: исходник → баннер → отдельный MP4 для каждого аккаунта → проверка → очередь публикаций → снимки метрик.

**Текущее состояние:** разработка. Локальная обработка проверяется отдельно от реальных платформ. Интеграции без входа пользователя не считаются проверенными. Полный день с 18 реальными публикациями ещё не принят.

## Установка и запуск

Нужны Python 3.13 и Node.js 24. В PowerShell из папки проекта:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup.ps1
```

Затем откройте ярлык **FrameFlow** на рабочем столе или **Start FrameFlow.cmd**. Открывается отдельное окно Windows через pywebview/WebView2. Диагностический адрес панели: http://127.0.0.1:8765. Сервер и рабочий процесс запускаются в фоне; закрытие окна не останавливает обработку. Повторный запуск возвращает существующее окно. Требуются установленный WebView2 Runtime и Chrome для интерактивного TikTok-входа. Компьютер должен быть включён и бодрствовать. На старте очередь приостановлена; включите её кнопкой «Запустить». Для полного выхода есть **Stop FrameFlow.cmd**: он останавливает сервер и worker этого проекта. Незавершённый рендер восстановится при следующем запуске; прерванная отправка потребует сверки результата.

Для разработки — два отдельных терминала:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8765
.\.venv\Scripts\python.exe -m backend.worker
```

Интерфейс в разработке: `cd frontend`, `npm.cmd run dev`. Сборка: `npm.cmd run build`. API: `/api/docs`.

## Каждый день

1. В монтажной загрузите видео и баннер PNG/JPG/WebP/GIF/MP4. Исходники копируются в `data/uploads`.
2. Настройте время, длительность, положение и размер баннера. Во вкладке «Варианты» выберите общие или персональные фильтры. Сохраните изменения.
3. Во вкладке «Публикация» задайте название, описание, видимость и свойства содержимого. Выберите аккаунты. Можно подготовить варианты для ещё не подключённых аккаунтов.
4. «В очередь» создаёт варианты одного исходника; в разделе очереди есть пакет всех исходников. Одинаковые сохранённые настройки не создают дубли. Для нового варианта измените настройки.
5. Запустите очередь, дождитесь обработки, скачайте и проверьте MP4. Предпросмотр браузера приблизительный: теплота и автоматическое отличие получателей окончательно применяются FFmpeg.
   Готовый файл можно открыть кнопкой «Посмотреть MP4» внутри задания. В монтажной есть «До / после» и скрытие баннера. Кнопка корзины убирает исходник только из списка; файл и задания сохраняются.
6. После просмотра явно подтвердите материал, конкретный аккаунт и видимость в задании либо нажмите «Разрешить отправку пакета» для готовых вариантов. В диалоге пакета показаны получатели и видимость каждого файла. Только после этого разрешена отправка. Без подключения аккаунта файл останется в ожидании.
7. Данные метрик появляются после успешного API-запроса. Отсутствие данных обозначено «—», а не нулём.

Пакет использует сохранённые настройки каждого исходника и получателей, выбранных у текущего ролика. Время ввода — выбранный пояс, в базе — UTC. Пропуск времени больше 10 минут требует подтверждения возобновления.

## YouTube

1. В Google Cloud включите YouTube Data API v3, настройте consent screen и тестового пользователя.
2. Создайте OAuth client типа **Desktop app**, скачайте JSON. Импортируйте его в настройках приложения локально.
3. Добавьте запись YouTube в «Каналы», нажмите «Подключение → Войти через Google». Имя и ID определяются через `channels.list(mine=true)`.
4. Для согласованного теста сначала используйте «Только я». Перед отправкой проверьте файл и аккаунт. Проекты Google без соответствующей проверки могут иметь ограничения публикации; фактический статус нужно проверять на платформе.

Адаптер использует возобновляемую загрузку и фиксирует возвращённый ID. Успешная загрузка сначала имеет статус «Обработка платформой». Статус «Обработан платформой» означает успешную обработку, а не открытый доступ: видимость остаётся выбранной. Потеря ответа переводит отправку в «Результат неизвестен» без автоматического повтора.

Если YouTube-ролик уже появился, у неизвестного задания можно выбрать «Сверить ID ролика». Проверяются канал и название через API. Отправка при этом не повторяется.

## Статистика

«Обновить метрики» запрашивает доступные данные подключённых платформ. Worker также делает почасовые снимки. В таблице показывается последний снимок, в «Динамике» — история выбранного ролика и показателя. Нулевое значение и отсутствие данных различаются.

Для ручного пути есть «Импорт CSV → Скачать шаблон»: в нём перечислены задания, исходники и получатели. Заполните счётчики и время снимка `captured` в ISO 8601 с поясом; сохраните CSV UTF-8 с запятыми. Источник помечается «Импорт CSV пользователя». Повтор того же задания/времени обновляет строку, а не удваивает метрики. Импорт не подтверждает публикацию и не заменяет подключение API.

## TikTok

Установлена `tiktok-uploader==1.2.0` с Playwright. Подготовлен адаптер, но фактический вход, идентичность аккаунта, отправка и получение ID **ещё не проверены**. Импорт локального JSON `{ "handle": "имя", "cookies": [...] }` защищает сессию DPAPI, но оставляет её неподтверждённой и не включает отправку. Не присылайте cookies в чат.

Для метрик предусмотрен отдельный TikTok Display API с разрешением `video.list`; браузерная сессия сама по себе такого доступа не даёт. Приватная утилита не должна рассчитывать на одобрение TikTok Direct Post без проверки условий платформы. Пока этот этап не пройден, TikTok-публикации не считаются работающей частью продукта.

## Хранение и надёжность

- `data/survivalflow.sqlite3`: база; `uploads`: оригиналы и баннеры; `exports`: готовые MP4; `temporary`: промежуточные файлы; `logs`: диагностика.
- `secrets/*.dpapi`: шифрование Windows текущего пользователя. Копия базы не включает секреты и видео. Перенос зашифрованных файлов на другой компьютер может потребовать повторного входа.
- «Копия базы» создаёт согласованную SQLite-копию в `data/backups`. Для восстановления остановите сервер/worker и замените базу из копии, сохранив текущую отдельно.
- Один worker обрабатывает одно видео/отправку одновременно. Пауза влияет на новые задания, текущий рендер отменяется отдельной кнопкой. Во время отправки отмена и слепой повтор запрещены.
- После аварии рендер ставится заново; начавшаяся отправка получает неизвестный результат. Ошибки загрузки не запускают повторную публикацию автоматически.
- «Очистка экспортов» в настройках удаляет только старые MP4 завершённых/отменённых заданий. Период задаётся в диалоге, по умолчанию 30 дней. Неизвестные отправки и ожидающие публикации сохраняются. Удаление запускается явно.
- Аппаратные кодировщики, автоматическая очистка и длительный нагрузочный прогон требуют отдельной проверки. По умолчанию используется `libx264`.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check backend scripts tests
```

Тесты используют отдельную временную базу, синтетические видео и отключённые аккаунты. Они не выполняют публикации. Описание дизайна — `docs/design/DESIGN_SPEC.md`; замороженный эталон не изменяется. Актуальная дорожная карта и журнал — в Obsidian, точный путь в `AGENTS.md`.

Браузер и настоящее прерывание процессов проверяет `scripts/verify_local.py`: передайте папку синтетических материалов, которую выводит `pytest -q -s`. Он создаёт отдельный каталог `data/validation-*`, проверяет принадлежность API и останавливает только свои дочерние процессы. Итоговые материалы — `docs/validation/v0.1`, описание — `docs/TEST_REPORT.md`.

Углублённая проверка и найденные исправления описаны в `walkthrough.md`. Для расширенного сценария выставьте `SURVIVALFLOW_VERIFY_EDGES=1` перед `verify_local.py`: проверяются 30 записей аккаунтов, длинные имена, ошибки диалогов, двойное сохранение и восстановление соединения. Это изолированная тестовая база; настоящие аккаунты не используются.


## Вход в TikTok

«Каналы → Подключение → Войти в TikTok» открывает отдельный Chrome. Пользователь сам проходит вход на TikTok, открывает собственный профиль и возвращается в FrameFlow. Панель показывает найденный @аккаунт; после подтверждения сессия сохраняется через DPAPI. Пароль приложение не читает. Отменить вход можно в панели; таймаут 10 минут. Ручной импорт остаётся запасным действием в «Расширенно».

Состояние `browser_login` не включает непроверенную автопубликацию. Реальная загрузка/ID/видимость/метрики проверяются отдельно; успешный вход не считается завершением этих интеграций. Локальная проверка: `tests/test_tiktok_login.py`, `scripts/verify_tiktok_ui.cjs`. UI-проверка намеренно имитирует переходы авторизации и не входит в реальные аккаунты.
